# onec-agent — открытый ИИ-консультант для 1С (v0.1, прототип)

Агент в стиле терминала прямо в форме 1С: сам изучает базу инструментами, показывает каждый шаг,
действия подтверждаются нативным диалогом 1С.

```
extension/   расширение 1С (префикс иик_): форма-чат, мост, исполнитель инструментов
server/      фундамент: цикл агента, реестр инструментов, веб-интерфейс, WebSocket
```

## Запуск (dev)

1. LLM: любой OpenAI-совместимый endpoint. По умолчанию LM Studio `http://127.0.0.1:1234/v1`,
   модель `qwen/qwen3-30b-a3b-2507` (контекст 32K). Переопределяется `ONEC_AGENT_*` (см. `server/onec_agent/config.py`).
2. Сервер: `server/run.sh` → `http://127.0.0.1:8765` (`/dev` — чат в браузере без 1С).
3. Расширение: `extension/deploy.sh <каталог файловой базы> [пользователь]`
   (импорт XML → проверка метаданных → проверка модулей тонкий/веб/сервер → применение).
   Если база опубликована через ibsrv — сначала остановить его (исключительная блокировка).
4. В 1С: раздел «ИИ-консультант» → «Адрес сервера…»: адрес сервера, затем токен доступа
   (сервер создаёт его при первом запуске в `server/data/token`).

## Сервер одним файлом (без Python)

`server/build-standalone.sh` собирает сервер PyInstaller'ом в `dist/onec-agent-server` (на Windows — `.exe`):
внутри `web/`, `evals/` (без `*.local.json`) и `notes/`, а `data/` (токен, профили моделей, вложения) и `logs/`
создаются рядом с файлом при первом запуске. Запуск — просто файл; порт и прочее — переменными `ONEC_AGENT_*`.
Сборка идёт на той же ОС, что и целевая: Windows-сборку делает GitHub Actions (`.github/workflows/build-server.yml`,
запуск вручную или по тегу `v*`, артефакты `onec-agent-server-windows` и `-macos`). Выгрузка исходников базы
(панель «Базы 1С») в сборке недоступна — ей нужны `ibcmd` и скрипт из `extension/`.

## Безопасность

- **Токен.** Без него сервер не откроет сессию чата и не примет файл: иначе любой, кто достучится
  до порта (в том числе чужая веб-страница в браузере — WebSocket не ограничен CORS), мог бы
  говорить с моделью от имени базы. Токен — `ONEC_AGENT_TOKEN` или файл `server/data/token` (права 600);
  в 1С хранится в настройках пользователя и в модель не передаётся. Для страницы `/dev` — `/dev#token=…`.
- **Сеть.** Сервер по умолчанию слушает только `127.0.0.1`. Выставлять его в сеть — только за
  обратным прокси с HTTPS: токен и данные базы идут открытым текстом.
- **Права.** Инструменты выполняются в сеансе и с правами пользователя 1С (безопасный режим, белый
  список); любое изменение данных — только после подтверждения в нативном диалоге 1С.
- **Облачные модели.** Выбор облачного провайдера — только администратором базы и с отметкой согласия
  на передачу данных. Ключи API хранятся на сервере агента (`server/data/models.json`, права 600)
  и в 1С/браузер не возвращаются. Не подключайте облако к базе с чужими персональными данными без
  согласия их владельца.

## Как устроено

- Цикл агента на сервере; инструменты выполняет расширение в сеансе и с правами пользователя
  (модуль не привилегированный, расширение в безопасном режиме, белый список инструментов).
- Мост форма ↔ страница — только строки и клики в DOM (`#bridge-out`, `#bridge-in`, `#bridge-btn`):
  веб-клиент 1С падает целиком на обращении к `window` страницы и вызове JS-функций из 1С.
  `<script>` в тексте поля HTML веб-клиент не выполняет — скрипт подключается через DOM.
- Защита от ошибок локальной модели: автоисправление запросов (литералы дат, опечатки ключевых слов,
  висящие СГРУППИРОВАТЬ ПО), предупреждение об обрезанной выборке, жёсткая остановка после 3 ошибок
  подряд (сервер отвечает сам — модель в этот момент выдумывает цифры).
- Памятка конфигурации: `server/notes/<Метаданные.Имя>.md` подмешивается в системный промпт.
- Журнал вызовов инструментов: `server/logs/audit.jsonl` (аргументы и сводки, без данных из базы).
- Вложения: 📎, перетаскивание, Ctrl+V. Скриншоты распознаёт vision-модель (по умолчанию Gemma 4 в LM Studio),
  Excel/CSV режутся на куски по 80 строк, PDF — по страницам, DOCX/текст — по ~3000 символов.
  Агент читает их инструментами `file_read` / `file_search` (выполняются на сервере, не в 1С).
  Файлы лежат в `server/data/uploads/<диалог>/`, удаляются по «Новый диалог» и через 72 ч.

## Исходный код конфигурации и база знаний

Оба инструмента работают в самом расширении, без сервера и без снятия безопасного режима.

- `code_read` / `code_search` читают тексты модулей из регистра расширения `иик_ИсходныйКод` (данные в базе).
  Наполняет его администратор один раз и после обновлений конфигурации:
  ```bash
  extension/load-sources.sh <база> [пользователь]                      # выгрузит конфигурацию сам (ibcmd)
  extension/load-sources.sh <база> [польз.] Конфигурация=<выгрузка> Расширение1=<выгрузка расширения>
  ```
  Источник — выгрузка «в файлы» (Конфигуратор или `ibcmd config export`); для БП 3.0 это ~19 тыс. модулей,
  ~1,1 ГБ текста. Код типовой конфигурации остаётся в базе клиента и в репозиторий не попадает.
  Ссылку из текста ошибки `{Документ.X.МодульОбъекта(512)}` можно передать как есть.
- `kb_search` ищет по своей базе знаний: статьи `kb/*.md` и решённые обращения `kb/tickets/*.md`
  собираются в макет расширения `иик_БазаЗнаний` скриптом `python3 extension/build-kb.py` (перед `deploy.sh`).
  Поиск лексический (BM25 по основам слов + совпадение фраз). Уверенные совпадения агент подкладывает
  к вопросу сам, отдельным видимым шагом: локальная модель часто не догадывается спросить базу знаний.

## Отчёты и правка

- `account_report`: ОСВ (по счетам первого уровня или по субсчетам, забалансовые — отдельным итогом),
  анализ счёта по субконто, карточка счёта с нарастающим сальдо; отбор по контрагенту.
- `report_run`: отчёты конфигурации на СКД через сам объект отчёта (отрабатывает его ПриКомпоновкеРезультата).
  Бухгалтерские отчёты БП (их настройки готовит форма) не формирует — отказывает и отправляет к `account_report`.
- `extensions_list`: расширения и доработанные ими объекты; с `object` — прямой ответ, изменён ли объект.
- `object_update`: правка реквизитов шапки; окно 1С «было → станет», по умолчанию «Нет»; проведённый документ
  перепроводится, а если не проводится — не записывается ничего; защита от записи поверх чужих правок.

## Источник модели (свой сервер или облачный API)

Кнопка «Настройки модели…» в форме консультанта (и ⚙ в шапке чата) — только для пользователя с правом
«Администрирование». Выбор на каждую базу отдельно:

- **Свой сервер** — любой OpenAI-совместимый endpoint в вашей сети: LM Studio, Ollama, vLLM. По умолчанию.
- **OpenAI-совместимый API** — OpenAI, DeepSeek, OpenRouter, YandexGPT (совместимый режим) и т.п.
- **Anthropic (Claude)** — Messages API, своя схема вызовов инструментов.
- **GigaChat** — OAuth по ключу авторизации, scope PERS/B2B/CORP; если корневой сертификат Минцифры не
  установлен, проверку сертификата можно отключить флажком.

Облачный провайдер сохраняется только с отметкой администратора «разрешаю передачу данных этой базы»
(кто и когда — записывается); в шапке чата при облаке всегда видно «☁ облако · провайдер · модель».
«Проверить подключение» отправляет провайдеру только «Ответь одним словом: готово».

Профили хранятся на сервере агента в `server/data/models.json` (права 600) по идентификатору базы
(хеш строки соединения). Ключ API в 1С и в браузер обратно не попадает: пустое поле при сохранении
оставляет прежний ключ. Пока у сервера агента нет авторизации (см. ограничения), признак администратора
приходит из 1С и прямым подключением к серверу в обход 1С может быть подделан.

## Модульные тесты сервера

```
.venv/bin/pip install -r server/requirements-dev.txt
.venv/bin/python -m pytest          # ~90 тестов, доли секунды; без 1С, без модели, без выгрузки БП
```

Покрывают: автопочинку запросов, проверку ответов и правил поведения в `/тесты`, защиты от выдуманных
цен и подсказки по датам, регрессию «тестовый прогон не уходит в 1С», подписи итогов бухрегистра,
базу знаний (поиск, стоп-слова, автоподстановку), код конфигурации на поддельной выгрузке, профили моделей
и согласие на облако, адаптеры Anthropic и GigaChat на поддельном сервере, вложения (Excel по частям,
CSV в cp1251, поиск), реестр и группы инструментов (заголовки шагов не падают на аргументах «не той формы»),
WebSocket сервера (приветствие, права на настройки).

## Тестовый набор (`/тесты`)

Вопросы к базе лежат в `server/evals/<Метаданные.Имя>.json`: вопрос + эталонный запрос. Команда `/тесты`
в чате для каждого вопроса сначала считает эталон живым запросом в 1С (тесты не устаревают при изменении
данных), затем агент отвечает с чистого листа, и все числа эталона должны найтись в ответе
(по модулю, точность 0,01). Итог — таблица в чате, подробности — `server/logs/evals/<время>.json`.

Набор для БП 3.0 — 15 вопросов: счета-фактуры, реализации, поступления, остатки 50/51/62, обороты 51/90.01,
справочник контрагентов, ОСВ по 51, карточка кассы, самый крупный должник. На `qwen3-30b-a3b-2507`
(температура 0) — 15 из 15, весь прогон ~2,5 минуты.

Результаты на демо-базе (35 тестов + сторож, 27.10.2026):

| Модель | Итог | Числа | Время |
|---|---|---|---|
| qwen3-30b-a3b-2507 (LM Studio, локально) | 34 из 36 | 16 из 17 | ~7 мин |
| GigaChat-3-Ultra (облако) | 29 из 36 | 16 из 17 | ~5 мин |

У GigaChat пять из семи провалов — попытка создать документ без товаров/цен или с неоднозначным
покупателем; в 1С такие попытки не уходят (их останавливают защиты сервера), но тест считает
саму попытку ошибкой.

Поведенческие тесты (`/тесты поведение`, 14 сценариев) проверяют не числа, а поведение: нужный инструмент,
никаких действий без запроса, уточняющий вопрос, честный отказ («удалить не могу»), не выдумывать долг
несуществующему контрагенту. Действия в прогоне перехватываются на сервере и в 1С не уходят; «сторож»
снимает снимок документов базы до и после прогона и проваливает его, если что-то изменилось.
Есть и многоходовые сценарии: «выставь счёт» → вопрос агента → «2 штуки по 3000» → счёт ровно с этими
данными. Сценарии, где нужны конкретные документы и контрагенты, лежат в наборе демо-базы; общий
набор `БухгалтерияПредприятия.json` подходит для любой базы БП 3.0. Свой набор для рабочей базы
кладите в `evals/<конфигурация>.local.json` (с запросом `detect`) — такие файлы в git не попадают.

### Демо-база

Облачные модели нельзя гонять на базе с реальными данными клиента, поэтому для сравнения моделей есть
демо-база: вымышленная ООО «Демо-Сервис» (ОСНО, НДС), 9 контрагентов, 6 позиций номенклатуры, закупки
и продажи за июль–октябрь 2026 со счетами-фактурами и оплатами, плюс черновики 26.10.2026 для
поведенческих тестов. Собирается из конфигурации БП без данных:

```bash
ibcmd infobase create --db-path=<база> --create-database --load=<бп.cf> --apply   # пустая БП
1cv8 ENTERPRISE /F<база> /C"ЗапуститьОбновлениеИнформационнойБазы"               # начальное заполнение
extension/deploy.sh <база>                                                          # расширение
ibcmd infobase dump --db-path=<база> clean.dt                                       # чистая точка
demo/make-demo.sh <база> clean.dt          # восстановить clean.dt и заполнить (demo/ДемоДанные.epf)
```

Генератор (`demo/src`) создаёт реализации и поступления функциями самого расширения. Для такой базы
набор тестов свой — `evals/<конфигурация>.demo.json`: в нём запрос `detect`, и `/тесты` выбирают набор
автоматически, если запрос нашёл в базе строку (здесь — организацию с ИНН демо-базы). Тестов
декларации НДС в демо-наборе нет: регламентированных отчётов в базе нет.

## Отчётность

- `regulated_report` — регламентированные отчёты, сохранённые в базе (декларации НДС, УСН, 6-НДФЛ, РСВ,
  бухотчётность): список и чтение показателей. Показатели лежат внутри отчёта (ДанныеОтчета: ПоказателиОтчета,
  многостраничные разделы, у бухотчётности — дерево разделов). Код ячейки декларации разбирается в раздел,
  строку и графу (П0003 00020 003 → раздел 3, строка 200, графа 3), а название строки берётся из макета
  самой формы отчёта (ячейка с тем же именем) — поэтому без ручных справочников и для любых форм.
- `vat_book` — книга продаж / покупок за период по регистрам НДСЗаписиКниги…: итоги и разбивка
  (ставка, контрагент, счёт-фактура, событие), дополнительные листы отдельно.
- `vat_reconcile` — сверка НДС за квартал: декларация (стр. 118, 190, 200, раздел 1 стр. 040) ↔ книги ↔ Кт 68.02.
  Проверено на III кв. 2026: 5 из 5 сходятся (разницы 0,31–0,76 руб. — округление декларации до рублей).

## Создание документов: сначала уточнить, потом создать

- Инструмент `ask_user` — уточняющий вопрос с вариантами-кнопками; вопрос завершает ход, ответ пользователя
  (или нажатая кнопка) продолжает диалог. Локальная модель охотнее вызывает инструменты, чем пишет текст, —
  вопрос оформлен инструментом, чтобы эта склонность работала на уточнение.
- Перед созданием счёта, реализации, поступления и элемента справочника сервер сверяет данные с тем, что
  назвал пользователь: контрагент, каждая позиция, количество (в т.ч. словами: «одна», «две»), цена.
  Подобранное моделью «похожее» («Услуга по обновлению прошивки ККТ», когда пользователь её не называл,
  «ИП» без фамилии) не проходит: действие не выполняется, в чате шаг «проверяю, хватает ли данных → нужно
  уточнить: …», модель спрашивает. Предложенное агентом и подтверждённое ответом пользователя — проходит.
- Про НДС, счета учёта, организацию, склад, единственный договор агент не спрашивает — их заполняет 1С.
- Варианты-кнопки к вопросу — только из найденного в базе за этот диалог или из слов пользователя
  (слова и все числа варианта должны там встречаться; «Другое», «Отмена» — можно). Придуманные моделью
  «Кабель ВВГ, 100 м, 150 руб.» отбрасываются (и пишутся в журнал сервера): нажатие такой кнопки выдало бы
  выдумку за слова пользователя.

## Защиты от выдумок модели

- Несколько документов с одним номером, а пользователь назвал дату — сервер подсказывает, какой подходит.
- Ответ после ошибки обращения к базе помечается «цифры не подтверждены данными».

## Мост и отбор инструментов

- Мост событийный: положив вызов в `#bridge-out`, страница «нажимает» скрытую `#bridge-ping`, форма ловит
  клик в `ПриНажатии` поля HTML и забирает вызов сразу (~50 мс). Таймер опроса 1С остался запасным путём:
  в скрытой вкладке браузер тормозит таймеры до минуты, а события — нет.
- Модели отдаются не все 28 инструментов, а группы под вопрос (`tools.GROUPS`): базовые всегда, «данные»,
  «диагностика», «действия», «файлы» — по словам вопроса; группы прошлого хода сохраняются для уточнений.
  Первый ответ модели — ~8,5 с вместо ~19 с.
- Если последнее обращение к базе перед ответом закончилось ошибкой, к ответу дописывается предупреждение,
  что цифры не подтверждены данными.

## Известные ограничения

- Локальная модель слабо рассуждает в диагностике: инструменты и база знаний дают ей верные факты,
  но вывод она может сделать неверный (например, причину «Поле объекта не обнаружено»).
- Память: Qwen3-30B с контекстом 32K занимает ~17–20 ГБ; на 48 ГБ рядом с 1С и браузером без свопа
  остаётся только одна модель.
- Сервер агента без авторизации: любой, кто может к нему подключиться, может говорить с агентом
  и (подделав признак администратора) менять источник модели. Токен — в ближайших планах.
- Отбор инструментов — по словам вопроса: необычная формулировка может не включить нужную группу
  (тогда по умолчанию даются «данные»).
